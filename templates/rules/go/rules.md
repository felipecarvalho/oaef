### Stack-Specific Architectural Rules (Go)

1. **Strict Anti-Suppression Policy**:
   - Suppressing static analysis or linter issues via `//nolint` or `//lint:ignore` is strictly forbidden.
   - **Permitted Scoped Deprecation Exception**: `//lint:ignore SA1019 <reason>` is permitted solely when invoking deprecated APIs from external Go modules during active transitional migrations.
   - **Permitted Code-Gen Exception**: The standard Go header `// Code generated by ... DO NOT EDIT.` is permitted to exempt machine-generated protobuf/mock files.
   - Blanket `//nolint` without specific linter rule names is strictly forbidden.

2. **Explicit Error Handling & Guard Clauses**:
   - Never ignore returned errors (e.g. `_ = doSomething()` is prohibited).
   - Check `err != nil` immediately using guard clauses, wrap context with `fmt.Errorf("...: %w", err)`, and return early.

3. **Interface Segregation Principle**:
   - Keep interfaces small (1 to 2 methods max, e.g., standard library `io.Reader`).
   - Define interfaces where they are consumed, not where they are implemented. Accept interfaces, return concrete structs.

4. **Handler Sizing & Clean HTTP Boundaries**:
   - HTTP handler functions and gRPC RPC methods must not exceed 30 lines.
   - Delegate request decoding, business logic execution, and response serialization to distinct functions or services.

5. **Safe Concurrency & Goroutine Lifecycles**:
   - Never spawn unmanaged goroutines. Always propagate `context.Context` for cancellation and timeouts.
   - Synchronize termination using `sync.WaitGroup` or channels to prevent leaks.
